# URL-first agent discovery and one authorised adoption

Reviewed 25 October 2026 (UTC). This records three fresh sessions against the
live site. It is evidence for [#376](https://github.com/loftwah/app-composer/issues/376),
with the existing prompt library ([#286](https://github.com/loftwah/app-composer/issues/286))
and setup surface ([#292](https://github.com/loftwah/app-composer/issues/292)).

## What was tested

| | Baseline | Post-change | Authorised adoption |
| --- | --- | --- | --- |
| Composer source | `5e012f98` | `f14fbf48` (Worker `df2040a5`) | `f14fbf48` |
| Seed | One URL + the issue's natural-language request | Same | Role-pack URL + explicit owner authorisation |
| Fixture | Fictional Python Field Notes, separate Git repo | Fresh copy, same fixture | Fresh copy, same fixture |
| Owner files changed | None | None | Only the authorised `docs/decision.md` and the report |
| Result | Grounded **no** to the platform, partly yes to practices | Same, and it found `/agent` | Documentation-only adoption; 7/7 tests before and after |

All three sessions were **OpenCode CLI 2.1.4** with
`opencode-go/deepseek-v4.1-flash` on macOS arm64. Each ran in its own fixture
directory with its own Git repository, no Composer `AGENTS.md`, no prior chat and
no pre-supplied guide. The fixture's own `AGENTS.md` was present and treated as
the project's trusted guidance.

## Baseline — before the public entry

Seed, verbatim:

> Look at https://composer.loftwah.com. Should we use App Composer for this
> project? What would it help with, what do we already do well, what is
> optional, and how would we adopt the useful parts? Inspect our project, ask me
> only about genuine choices, and do not change anything until I authorise it.

What it found from the homepage: `/architecture`, `/guide`, `/setup` and `/init`.
It did **not** reach `/prompts` or `/roles` from the first hop.

Outcome: **no to App Composer as the platform; partly yes to two habits**
(evidence/check discipline and a written handoff). It identified the fixture's
stdlib constraint, ran the existing 7-test suite, and left every recorded owner
file byte-identical. It proposed a docs-only change but did not make it.

## Post-change — live public entry

The release added `/agent`, a versioned `/agent.md`, the **Should we use App
Composer?** prompt module and links from the homepage, `/prompts` and `/setup`.

With the same seed and a fresh fixture, the agent:

- found the homepage link and fetched `/agent` explicitly among its first public
  paths;
- separated what Composer is, what fits, what the project already does well and
  what is optional;
- returned **no to the platform, partly yes to two practices** and named the
  unverified items;
- left `owner-note.txt`, `site.json`, `notes.json` and `scratch/owner-draft.txt`
  byte-identical, with no untracked files.

## Separately authorised adoption

A third fresh session was given an explicit, narrow authorisation:

> Read the public Programmer role pack at
> https://composer.loftwah.com/roles/programmer and use its output section
> exactly. […] The owner has read the Composer fit assessment and authorises
> exactly one documentation-only change: create `docs/decision.md` recording
> that this project adopts App Composer's evidence-and-handoff discipline as
> practices, not the App Composer platform. […] Do not modify `app.py`,
> `site.json`, `owner-note.txt`, `scratch/`, `README.md`, `AGENTS.md` or
> `test_app.py`. […] Run `PYTHONDONTWRITEBYTECODE=1 python3 -m unittest -q`
> before and after, write `role-output.json` using the pack's Programmer fields,
> and report the exact before/after result and files changed.

Observed:

- **Before:** 7 tests, `OK`, exit 0.
- **After:** 7 tests, `OK`, exit 0.
- `docs/decision.md` created with the adopted practices, check command,
  owner-owned files and the explicit no-EmDash/no-Cloudflare decision.
- `role-output.json` uses the pack's eight fields. `PR` honestly says none and
  names the missing remote/review path; `Reviewer` records that no separate
  human reviewer was supplied.
- Owner file hashes unchanged; no `__pycache__`, `.pyc`, install, account,
  deployment or migration.
- The agent did not self-approve, merge or deploy.

## What this proves

- One wholly unaware local agent, given only the product URL and an ordinary
  owner request, can discover the public product, inspect an unrelated project
  read-only and return a grounded fit/no-fit decision.
- The new `/agent` entry is reachable from the homepage and is used without
  coaching.
- A separate, explicitly authorised session can consume a maintained public
  role pack and complete one reversible change with before/after tests, while
  preserving owner work and refusing self-approval.
- A no-fit answer is a successful outcome: the fixture kept its stdlib stack.

## What this does not prove

- One client and one model only. No second client, model or host was exercised.
- The fixture is fictional and local, not a real customer repository. The
  adoption is a documentation-only change, not a customer migration.
- The interactive question tool is unavailable in a non-interactive run; the
  agents listed the genuine owner choices in text instead. That is a harness
  limitation, not a product result.
- No physical device, screen reader, external unfurl or authenticated owner
  acceptance.
- No production modification was made by any agent. The only production change
  was the separately verified Composer release.
- `/prompts` and `/roles` were still not reached from the first hop in the
  post-change run; the explicit `/agent` link is the reliable path.

## Reproduction notes

The fixtures and harness are the existing `labs/fresh-agent/` assets. The two
assessment sessions used `prepare --case existing-change` and then removed the
unrequested role-pack copy; the adoption session supplied the public role pack
URL instead. Raw transcripts stay in the ignored `output/` directory and are not
committed because they contain host-local paths and transient browser output.
