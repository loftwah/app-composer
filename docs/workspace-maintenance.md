# Workspace maintenance and approved-content portability

The native **Workspace maintenance** page reads a saved Guestbook instance through the current authenticated Creator workspace. Check its connection, then prepare an approved-content file when the app's exact pinned source supports it. Owners and editors may export private app-owned content; viewers may inspect connection metadata and retain the existing stack-configuration export. Workspace membership never grants global mini-app administration.

A check compares the fixed server connection's source, account, environment and target with the app-owned resource and active configuration. Saved revision, binding and current membership are checked again after remote reads. It does not change the saved draft, publication, resource confirmation or operation journal. Unresolved operations, changed confirmations, unsupported contracts and failed reads remain explicit; reconnect/reconcile stays in Creator stacks. Checks show their timestamp and expire in the UI after five minutes. They are observations, not ongoing health guarantees.

Exact identities appear in a disclosure. Worker deployment IDs, total media coverage, metrics and costs are unavailable through this contract and are never inferred from a successful build-status response. Other apps have no owned-resource maintenance or approved-content export here. No provider account, policy, credential or runtime setting is created or changed.

The app-owned `guestbook.approved-portable/v1` file contains the active configuration, current source identities, up to eight original approved contributions, their sanitised PNGs and SHA-256 digests, and explicit included/eligible counts. Missing images and larger approved selections produce partial coverage. Private items, prior restored copies, legacy global owner content, credentials, other apps, third-party data and infrastructure are excluded. Downloading the file grants no new licence. Retain contributor consent and confirm permission to copy.

The independent Guestbook app's supported server API restores only into fresh private, paused identities, with pending items and no active publication. This native page does not dispatch restores. The app requires its current exact source build, authorized workspace/account/environment/target, live original approved item revisions/configuration and matching PNGs. It never overwrites a resource or tombstone. Retained lineage guards later approval, public/provider reads and private copy-media requests. Hide/delete, changed source revisions/configuration, or missing/changed source PNGs deny copied media; hiding then reapproving a source does not authorize an older copy.

A file alone cannot revive eligibility. This dependent portability path cannot restore a lost source database, work offline, or cross accounts/environments. Code rollback does not restore app data/media. No complete backup, point-in-time recovery, retention, zero-loss, downtime, capacity or cost-cap guarantee is made. Downloaded files outside controlled app routes cannot be recalled. The app's D1 receipt and private R2 media have separate commit boundaries; unknown restore outcomes require operation reconciliation before retry and may retain inaccessible private objects for investigation.

Required release evidence remains exact source/pin, forward Guestbook migration `0003_portability_lineage.sql`, native host interaction and app-owned Worker/D1/R2 restore/revocation proof. Local fixtures and a successful build do not establish a production restore, full account recovery, physical-device acceptance or permission to restore owner records. Use fictional isolated resources only for qualification.
