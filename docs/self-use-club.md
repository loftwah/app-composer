# Self-use club: one honest account

25 October 2026. This records one complete App Composer self-use journey: a
fictional club was described in Composer's real public forms, the exported
artefacts were given to a fresh local agent, an app was implemented in an isolated
directory, and a second request was applied to the running app without losing
content.

**This is one recipe, not proof of general autonomous app creation.** Composer
produced prompts and a portable specification. An agent made the implementation
decisions and wrote the application. Both halves are separated below.

## What was used

- Composer source `86514680720702ce30157671652981e388b77f65`; production
  `/build.json` returned the same commit on 2026/10/25.
- The real production pages `https://composer.loftwah.com/setup`,
  `/prompts#build`, `/prompts#change` and `/init/content`. No account or owner
  draft was required or touched.
- A fresh local worktree at `labs/self-use-club/app`, Node 22.23.4, Wrangler 4.152.0,
  local D1 and Chromium through Playwright.
- Fictional people, club, addresses and records only. No deployment, Cloudflare
  account, resource, DNS, Access policy, secret store, email or payment.

## What Composer generated

The exact files are committed under [`labs/self-use-club/spec/`](../labs/self-use-club/spec/README.md).

| Composer route | Output |
| --- | --- |
| `/setup` (New project, inspect and adapt, download) | `project-setup.md` |
| `/prompts#build` (Build an app, download) | `requests/build.md` |
| `/init/content` (brief → copy design request → import agent model → download) | `requests/*.design-request.md`, `models/*.model.json`, `models/*.downloaded.seed.json`, `handoffs/*.md` |
| `/prompts#change` after the first run | `requests/volunteers.md` |

The guide is a complete project-instruction document, not a readiness receipt.
The build and change requests are portable agent handoffs. The models include
groups, required fields, lengths, choices, a calendar date and starting values;
each model was validated by Composer on import and the downloaded seed was
regenerated by Composer's own library.

The model JSON bodies were **written by the agent** from Composer's generated
field-design request. The editor documents that loop: describe the form, give the
request to an agent, import the returned version-1 model. Composer validated and
exported the result, but did not invent the field structure. The application code
was not generated by Composer.

## What the agent implemented

The worker, database, interface, tests and acceptance scripts were agent work:

- Cloudflare Worker with plain TypeScript, server-rendered HTML and one CSS file;
  no client JavaScript and a `script-src 'none'` CSP.
- App-owned D1 schema in `migrations/0001_init.sql` for events, notices and
  enquiries. `migrations/0002_volunteers.sql` was added by the second request.
- Public routes: home, events, event detail, notices, joining enquiry and
  volunteer roles/sign-ups.
- Private owner area: server-checked local bearer token exchanged for an
  `HttpOnly`, `SameSite=Strict` cookie; create/edit/publish events and notices;
  review enquiries; create/edit/publish volunteer roles; inspect private sign-ups.
- Real empty, validation, 401, 404, 409 and 500 states. No fake success. No email
  is sent and no payment is taken.
- Tests run the actual Worker against a `node:sqlite` D1 adapter and a populated
  database for the additive migration.

### Mapping from the exported models to D1

| Exported model key | D1 column | Note |
| --- | --- | --- |
| `events.title`, `summary`, `description`, `event_date`, `start_note`, `location`, `cost`, `publication` | same names | `publication` is `Draft`/`Published` |
| `notices.title`, `body`, `notice_date`, `publication` | same names | |
| `enquiries.name`, `email`, `phone`, `enquiry_type`, `message`, `review_state`, `review_note` | same names | `status` is reserved by EmDash's schema, so the model deliberately used `review_state` |
| additions | `id`, `slug`, `created_at`, `updated_at`, `published_at`, `reviewed_at` | Agent implementation choices for routing, ordering and review time |

The volunteer feature did not get a fourth content-model export. The second
request was expressed with Composer's change prompt only, and the agent designed
the `volunteer_roles`/`volunteer_signups` tables. That is a gap, not something to
dress up as Composer-generated schema.

Other agent decisions: the club identity and copy, the river mark, the section
order, seed content, the capacity model (confirmed sign-ups counted against a
hard limit), `409` for a race-lost place, and the local token/session mechanism.
The brief constrained the stack, local-only run, Australian English, date handling
and server-enforced owner access.

## What required human intervention

No human sign-in, purchase, permission grant or MP decision was needed. The public
Composer forms are anonymous, the local app needs no account and the owner token
is a local fictional value.

The invoking coordinator supplied the fictional club idea and the run constraints.
The executing agent chose the routine implementation. A real user would still need
to choose an idea, accept fictional versus real content and decide whether to
deploy; none of that happened here.

Two environment-level interventions were needed:

- The repository's installed Node 22.23.1 is below Astro 7.4.2's `>=22.23.4`
  requirement, so the already-installed Node 22.23.4 was put first on `PATH` for
  Composer commands. No new runtime was installed.
- This host defines an unrelated `ADMIN_TOKEN`. The first committed acceptance
  script inherited it and the owner login correctly refused it. The script now uses
  `RIVERTON_ADMIN_TOKEN`; the database was reset and both recorded runs were clean.

## What broke or was clumsy

1. **Three models downloaded under the same filenames.**
   `app-composer-content-model.json` and `emdash-content-seed.json` were reused for
   every collection, so the browser renamed collisions. Fixed in this worktree:
   `contentModelDownloadNames()` now emits `events.app-composer-content-model.json`
   and `events.emdash-content-seed.json`, with tests.
2. **“Keep my stack” was offered to a new project.** The `/setup` select said
   “Keep my stack / inspect and adapt” even when “New project” was selected.
   Changed to “Let the agent inspect and adapt”; the project-setup suite asserts it.
3. **The content model has no time-of-day field.** The event model has a calendar
   day plus a free-text `start_note` (“7:00 am for a 7:30 am start”). The editor
   documents the missing time, so this is a known format limit rather than a
   surprise, but a club app needs times.
4. **There is no multi-model bundle export.** The club needed three collections;
   each was a separate download and the bundle manifest was assembled by hand.
   No competing CMS or bundle engine was added to Composer.
5. **Code before migration breaks the public site.** Applying the volunteer code
   while the local database still had only `0001` made `/` return 500
   (`no such table: volunteer_roles`). The fix is release ordering: apply additive
   migrations before serving code that uses them. This is recorded rather than
   hidden by a catch-all fallback.
6. **Native date controls display the browser locale.** Stored dates are
   `YYYY-MM-DD` and public copy is `YYYY/MM/DD`, but a browser date picker may show
   `07/11/2026`. Admin date fields now explain this. Replacing the native picker
   would be a product decision, not a silent fix.
7. **Composer's local Astro dev server could not start under the host's default
   Node.** This is environment drift, not a Composer logic defect. The exact
   version needed is now written in the run notes.

## Second request, without losing content

The request was exported from the real `/prompts#change` form as
[`requests/volunteers.md`](../labs/self-use-club/spec/requests/volunteers.md):
add volunteer roles with a capacity, public sign-up and remaining places, preserve
all existing content, one additive migration, server-enforced limit.

The agent implemented:

- `migrations/0002_volunteers.sql`: creates `volunteer_roles` and
  `volunteer_signups` plus two indexes. No `ALTER`, `UPDATE`, `DELETE` or insert
  into an existing table.
- `src/db.ts`: role queries compute `taken`/`remaining`; sign-up is one conditional
  `INSERT … SELECT` that only writes while a published role has a free place.
- `src/validate.ts`: role and sign-up validation.
- `src/render.ts`, `src/admin-view.ts`, `src/worker.ts`, `src/styles.ts`: public
  volunteer pages, home section, owner form/list and publish controls.
- `tests/worker.test.mjs`, `tests/migration.test.mjs`: capacity, full-role,
  invalid-sign-up, admin control and additive migration cases.
- `scripts/acceptance-volunteers.mjs`: the browser journey and captures.

Recorded result: capacity 2 → two sign-ups → full → a third POST refused with 409;
owner raised capacity to 4 and changed the title → both sign-ups remained and the
public page showed `2 of 4`. Existing notices and enquiries were byte-identical;
the intentional event edit and reviewed enquiry survived. Exact rows are in
[`second-feature-preservation.json`](evidence/selfuse-club-20261025/second-feature-preservation.json).

## Exact reproduction

```sh
# Composer side, from the repository root
pnpm install --frozen-lockfile --prefer-offline
node --test tests/content-model-downloads.test.mjs tests/project-setup.test.mjs
pnpm check

# Fresh local app
cd labs/self-use-club/app
pnpm install --prefer-offline
rm -rf .wrangler
pnpm exec wrangler d1 execute riverton-rowing-club --local --file=migrations/0001_init.sql
pnpm db:seed
pnpm exec wrangler d1 execute riverton-rowing-club --local --file=migrations/0002_volunteers.sql
pnpm check
pnpm build
pnpm dev          # http://localhost:8787
```

In a second terminal, with a Playwright module already on the host:

```sh
export PLAYWRIGHT_MODULE=/absolute/path/to/playwright/index.mjs
node labs/self-use-club/scripts/acceptance.mjs
node labs/self-use-club/scripts/acceptance-volunteers.mjs
```

The admin token is the local fictional `riverton-local-admin-2026` passed by
`pnpm dev`; override the scripts with `RIVERTON_ADMIN_TOKEN` if changed.

Recorded checks: app **18/18 tests**, app dry-run build **103.74 KiB / 22.14 KiB
gzip**, acceptance **10 + 10 steps** with no unexpected console errors and no
horizontal overflow, Composer focused tests **14/14** (3 download-name tests plus 11 project-setup tests; the download-name suite is also 3/3 on its own).

Root commands on this worktree: `pnpm build` passed (Astro build plus the
publication guard: 1243 files, 150 archive members). `pnpm check` ran **1020 tests:
1018 passed, 2 failed**, both unrelated to this lane. The failures are
`two-team programme exercises actual pinned Guestbook code…` and
`exact selected Guestbook HTML changes raw nonce hashes…`; they read the local
sibling checkout at `376129c8b48d29d26e982777084aa241966569c7` while the pinned
source is `5075d7be53b43aca288d3707fd06851aca91e8c2`. No Guestbook source was
modified by this lane. The focused Composer suites and all 18 app tests are green.

## Proven and not proven

Proven for this run:

- real public forms produced the committed guide, prompts, three validated
  models/seeds/handoffs and a change request;
- an agent built a working local app from them, with real D1 data and server-side
  owner authorisation;
- visitor submit → owner pending → review, anonymous denial, validation refusal,
  owner edit → public change;
- capacity-limited volunteer sign-up, full-role refusal, owner capacity change and
  existing-content preservation;
- phone and desktop rendering in both themes, with no horizontal overflow.

Not proven:

- that Composer can autonomously create arbitrary apps or that most Composer code
  originates in its forms;
- a deployed app, production D1, custom domain, provider auth, email delivery,
  payment, backup or restore;
- multi-user invitations/roles, rate limiting, audits, concurrency under load, or
  screen-reader/physical-device acceptance;
- that the two small Composer fixes are live; they are worktree changes with tests,
  not deployed output.

The evidence index, screenshots and replay scripts are in
[`docs/evidence/selfuse-club-20261025/`](evidence/selfuse-club-20261025/README.md).
