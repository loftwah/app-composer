# The first governed application path

Reviewed 23 October 2026. Owners: #216/#218/#219/#220/#221/#257; release identity and actual production observations belong to #11.

An admitted Composer creator can open **Internal platform** in native EmDash administration. Select a new, empty workspace through Workspace access first. Existing applications cannot yet be adopted into platform mode. The workspace remains managed after its first policy is saved; disabling the policy pauses requests and does not reopen legacy lifecycle APIs.

A current workspace owner establishes the standing policy: supported Guestbook recipe, synthetic data, preview intent, small quota, and optional independent review. An editor or owner can request an application; a viewer can inspect its workspace only. A profile or imported specification never changes these roles. Enterprise admission, EmDash administration, Composer membership, delivery credentials, runtime bindings and application access remain separate.

The first recipe creates one app-owned visitor-book resource on the existing pinned Guestbook Worker, then publishes an immutable Composer stack page. It uses the existing application database and its workspace/account/environment-scoped resource protocol. It does not provision a new Worker, D1, R2 bucket, customer identity or isolated production environment. The request's preview intent and the actual production runtime identity are displayed separately. Guest submission stays closed, and only fictional data is supported. Australian-only handling, the knowledge recipe and production promotion are unsupported on this path.

## Request, update and review

The same validated request produces the readable plan, existing version-2 app spec and scoped agent handoff. The plan includes exact independent source, configuration, target, policy revision, resource intent and verification. Credentials are never exported.

Routine permitted requests run automatically through the existing trusted app-resource adapter. There is no arbitrary build endpoint or always-online external agent runner. An absent connection leaves the operation waiting. The server rechecks current acting/requesting membership, exact plan/source/target, policy, applicable separate approval and its expiry before effects and publication. Publication has a transaction-level request/stack/lease/policy guard. Ordinary lifecycle APIs cannot bypass managed mode, including a mutation that began before policy registration.

When independent review is enabled, a different current owner can accept, send back with a reason or deny the exact plan. Acceptance runs a connected permitted operation. A revision clears the prior approval and is evaluated again. A sent-back or denied update can be corrected while retaining its existing application.

A completed request offers **Plan an update**. The supported update changes its title/configuration through the same policy path, retaining stack and resource identity and the existing immutable publication/configuration history. This is not arbitrary source-code migration or production promotion.

## Interrupted operations

Submission keys, request leases and the existing resource-operation journal prevent a refresh or retry from blindly creating another book. A lost acknowledgement remains uncertain. The previous resource/operation identities are retained; completed external effects are reconciled before continuing.

If policy changed while an app outcome was uncertain, **Check previous operation** performs scoped read-only provider reconciliation without resubmission. Once the journal is known, revise the request against current policy. Pre-effect expired approvals can also be replanned and reviewed again. A changed candidate or unknown provider state must be inspected; the system does not silently overwrite it or delete resources.

**Complete** records exact source/resource/configuration checks plus independent unauthenticated HTTP reads of the app and its composed publication. Responses must match the expected title, resource path, canonical URL and publication identity. It is a dated operation result, not continuous monitoring or a guarantee of future service health. Missing/removed publications remain inspectable as needing attention.

## Operating and evidence boundaries

Native workspace controls retain app-owned content moderation, supported approved-content/media exports and existing maintenance links. Request events retain the actor, action, exact plan digest and plan document. These are operation records, not provider billing, unique visitors or a complete observability platform. New vendor delivery, incidents, remediation and full runtime telemetry remain separately qualified work in #215/#220/#255.

Retirement, automatic resource deletion, credential rotation, promotion, full data restoration, provider exit and commercial customer admission are not implemented by this slice. Retained resources continue to count against the application quota. Existing sensitive-state restrictions remain intact.
