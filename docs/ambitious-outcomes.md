# Ambitious outcomes

Owner direction recorded **2026/11/28 Australia/Melbourne (AEDT, UTC+11) / 2026/11/28 UTC**: the approach in [Felix Rieseberg's article](https://felixrieseberg.com/how-to-be-more-ambitious-a-tutorial-for-humans-with-models/) is what the portfolio should practise. The article distinguishes speed, altitude, depth and range: faster execution, responsibility for the intended outcome, stronger methods and evidence, and useful contributions from other disciplines. The operating direction below applies that idea to our own products and existing delivery rules.

## Choose the useful result

For an authorised task, establish what should become possible for the user and why it matters. Read the current owning issue, relevant decisions and actual implementation before choosing the next move. Name a concrete ambitious target and the evidence that would demonstrate it. An initial request may omit ordinary professional work needed to finish the result; supply that judgement instead of making the owner discover each omission.

Keep the user's chosen task boundary. A narrow correction stays narrow. A broader opportunity can be recorded with its expected benefit and next action; this guidance alone does not activate the whole backlog, authorise spending or start a recurring process. Treat a difficult target as a hypothesis to investigate. Report measured limits and failed attempts honestly.

Composer's mission is useful, retained Cloudflare Workers AI adoption through excellent owned outcomes and the user's chosen agent. Internal evaluation tokens, question counts, features added and issues closed do not establish that outcome. Preserve standalone products and their own data, source, identity and release boundaries.

## Work with the evidence and tools the result needs

Use the least processed relevant material available: the actual source and build, real failure logs, job and usage records, original media, saved owner feedback and the current user journey. Summaries help locate evidence; they cannot replace inspection of a claim that matters to the change. Record unknowns and missing access precisely.

Select concrete professional methods for the task. Examples include profiling the slow interaction, tracing a failed job to its source revision, inspecting composition at the intended display size, listening to the complete exported film, or comparing a claim with an actual adoption event. Technical correctness, creative quality, publication and owner satisfaction remain distinct.

Bring in other disciplines when their methods can change the result: product research, interaction design, engineering, cinematography, editing, audio, accessibility or distribution. Give collaborators bounded work, shared inputs and an output another worker can use. Relevant tools and actual outputs establish the contribution; expert-role prose does not. Keep at most two active implementation units and one integration owner. Useful read-only investigation can run independently.

Use existing capability discovery, MCP, CLI and computer-use routes within their current authority. A listed tool, installed skill or generated plan is not proof it was used. Resolve a missing prerequisite when authorised, identify the exact unsupported operation otherwise, and continue useful independent work. Model/provider choice stays evidence-led and compatible with BYO agents.

## Make the result observable

Choose the smallest independent signal that answers the actual claim: a measured trace, file hash, current release identity, saved-and-reopened state, real user interaction, rendered output, listening review or relevant independent critique. The generating model's self-score is insufficient. Reuse valid evidence; independent verification does not require a new auditor, benchmark suite or approval stage for every edit.

Carry ordinary work through the existing review, merge and release route. The routine budget is **120 seconds from first relevant edit to the verified destination**, including checks and handoffs. If it overruns, retain the original clock, name the bottleneck and continue resolving it. Do not hide an overrun, interrupt a mutation or weaken a meaningful safeguard. Larger creative or research work has a stated scope and budget, separate from routine release prerequisites.

Documentation-only work finishes on main with its focused diff/link/contract check. Runtime changes need their affected deployed or packaged flow. Preserve the difference between guidance adopted, behaviour exercised and outcome delivered. An owner-satisfaction incident stays open until the owner's explicit satisfaction; useful repair attempts can ship while it remains open.

Retain the relevant source, decision, accepted and rejected elements, result and next action in the existing issue or product record. A resumed agent should use the lesson and improve the next attempt. Creating another issue or acknowledgement alone is not learning.
